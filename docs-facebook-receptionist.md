# Facebook virtual receptionist

Uses the existing Tuff Bros OS Meta app (1501428735133190) and Tuff Bros Mobile Detail Page (794494190410669). Public HTTPS callback: https://tuffbrosdetailing.com/.netlify/functions/receptionist-facebook. The operations workspace remains private.

Owner setup is in VR → Facebook leads & Messenger. The Meta app secret is entered through a password field, saved encrypted in OS, and transmitted through the existing Ed25519-signed website bridge into encrypted Netlify storage. The existing Page token and email sender are copied server-side; neither appears in browser responses. The webhook verify token is revealed only in the owner-only setup view.

Configure the callback in Meta; subscribe the Page to messages, message_echoes, and leadgen. Complete Meta customer-access approval. The Nov 14 inspection found pages_messaging and pages_manage_metadata “Ready for testing,” no callback, and publication disabled pending the privacy-policy URL. The site privacy page now describes the actual receptionist data flow and provides data request instructions at /privacy/#data-deletion. It does not establish Meta approval by itself.

After Meta approval, disable competing Facebook instant/AI replies, check Page subscriptions, confirm access in VR, select reviewed detailing lead-form IDs, and set a monitored reply email. Enable Messenger and lead-form email independently. No historical imports or events predating activation trigger sends. Unknown forms, missing emails, attachments, stop requests, expired events, provider failures, and human takeover go to review. Messenger targets only the incoming Page-scoped sender; never phone/email/name matching. The initial email uses Resend with a deterministic idempotency key and the selected Reply-To inbox. Subsequent email replies are handled by the team in that inbox; AI email continuation is not implemented.

Incoming signed events are stored before worker dispatch. Netlify background invocation handles AI/provider latency and retries busy processing. Per-event and per-conversation compare-and-swap locks prevent overlapping work. Sends persist an attempt before the network request; missing/ambiguous receipts are held and are not sent again automatically. Accepted means provider acceptance, not delivery/read. One initial email attempt per address per UTC day also prevents duplicate forms from producing multiple initial emails. Global AI budget is shared with website/voice; twenty AI turns per conversation. The same saved response preferences, catalog, and no-price/no-booking-commitment rules apply.

Recent Facebook activity and takeover controls are in VR. The existing Lead Recovery Messenger adapter remains read-only and historical; its bounded snapshots do not prove live coverage. Existing Windsor lead-form import remains separate and does not trigger these replies. No automatic CRM identity merge, booking, quote acceptance, payment, SMS consent, or old-customer outreach is created by the webhook.

Disconnecting the Page or email integration disables the corresponding website sender before removing OS credentials. VR disconnect removes the automatic connection secret/token, while retaining activity for review. Meta authorization must be revoked separately if desired.

Primary references: https://developers.facebook.com/docs/messenger-platform/getting-started/quick-start ; https://developers.facebook.com/docs/graph-api/webhooks/getting-started/webhooks-for-leadgen ; https://docs.netlify.com/build/functions/background-functions/ ; https://resend.com/docs/api-reference/emails/send-email .
